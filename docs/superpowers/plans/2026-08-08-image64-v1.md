# image64 v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking. **Dispatch each task to an Opus 5
> subagent** (`model: opus`). Do not start implementation until the
> maintainer says go.

**Goal:** Build image64 per the approved spec
(`docs/superpowers/specs/2026-08-08-image64-c64-converter-design.md`): a
C64Kit conversion engine, an `image64` CLI, and a SwiftUI app, all sharing
one `ConversionOperation`.

**Architecture:** One SwiftPM package, three targets. `C64Kit` (library) owns
the whole pipeline — palette, dither, cell constraints, packing, file
writers, `ConversionOperation`. `Image64CLI` (executable product `image64`)
and `Image64App` (executable) are thin front ends over
`ConversionOperation`. No `.xcodeproj`: Xcode users open `Package.swift`;
agents use `swift build` / `swift test` / `swift run`.

**Tech Stack:** Swift 5.10, SwiftPM, macOS 14+, SwiftUI, CoreGraphics /
ImageIO / CoreImage, swift-argument-parser (CLI target only).

## Global Constraints

- Swift tools version 5.10; platform `.macOS(.v14)`.
- The only third-party dependency is `swift-argument-parser` (>= 1.3.0), in
  the `Image64CLI` target only.
- `C64Kit` must not import SwiftUI or AppKit. CoreGraphics, ImageIO,
  CoreImage are allowed.
- **App/CLI lockstep:** front ends call `ConversionOperation` and never
  reimplement any part of it (AGENTS.md cardinal rule).
- **Preview-from-packed-bytes:** every preview/PNG pixel comes from
  `C64Image.render(palette:)` over the packed bytes, never from an
  intermediate.
- All frequency ties break toward the **lower palette index** — everywhere.
  This makes every algorithm deterministic and testable.
- Commit style: `type(scope): summary` (`feat(engine): …`, `test(cli): …`).
  Commit locally; never push.
- TDD: every task writes its failing tests first. Keep `swift test` green at
  every commit.
- Verification commands are plain form: one command, executable first (no
  `cd &&`, no env-var prefixes) — AGENTS.md allowlist rule.

## Reference: pinned C64 facts (used by Tasks 4–7)

Every task below that touches bytes uses these exact definitions; they are
the authoritative copy for this plan.

**Bitmap layout (both modes).** 8000 bytes = 25 cell-rows × 40 cells ×
8 bytes. The 8 bytes of a cell are its pixel rows top-to-bottom:

    bitmapOffset(cellRow, cellCol, rowInCell) = cellRow*320 + cellCol*8 + rowInCell

**Hires (320×200, cell 8×8).** In each bitmap byte, bit 7 is the leftmost
pixel. Bit = 1 → the cell's screen-RAM **upper** nibble color; bit = 0 →
**lower** nibble color.

**Multicolor (160×200, cell 4×8).** Each bitmap byte holds 4 double-wide
pixels, 2 bits each, leftmost pixel in bits 7–6. Bit-pair meaning:

| pair | color source |
|------|--------------|
| `%00` | shared background byte |
| `%01` | screen RAM upper nibble |
| `%10` | screen RAM lower nibble |
| `%11` | color RAM low nibble |

**Screen/color RAM.** 1000 bytes each (40×25, row-major: `cellRow*40 +
cellCol`). Color RAM uses only the low nibble; writers set the high nibble
to 0.

**Koala (.koa).** 10003 bytes: `0x00 0x60` (load address $6000,
little-endian), bitmap 8000 @ offset 2, screen RAM 1000 @ 8002, color RAM
1000 @ 9002, background 1 @ 10002.

**Art Studio (.art).** 9009 bytes: `0x00 0x20` ($2000), bitmap 8000 @ 2,
screen RAM 1000 @ 8002, 7 zero bytes @ 9002.

**Palettes.** Exact sRGB values (r, g, b):

| # | name | Colodore | Pepto |
|---|------|----------|-------|
| 0 | black | 000000 | 000000 |
| 1 | white | FFFFFF | FFFFFF |
| 2 | red | 813338 | 68372B |
| 3 | cyan | 75CEC8 | 70A4B2 |
| 4 | purple | 8E3C97 | 6F3D86 |
| 5 | green | 56AC4D | 588D43 |
| 6 | blue | 2E2C9B | 352879 |
| 7 | yellow | EDF171 | B8C76F |
| 8 | orange | 8E5029 | 6F4F25 |
| 9 | brown | 553800 | 433900 |
| 10 | light red | C46C71 | 9A6759 |
| 11 | dark grey | 4A4A4A | 444444 |
| 12 | grey | 7B7B7B | 6C6C6C |
| 13 | light green | A9FF9F | 9AD284 |
| 14 | light blue | 706DEB | 6C5EB5 |
| 15 | light grey | B2B2B2 | 959595 |

**Nearest color.** Weighted squared distance over sRGB byte components:
`0.299·Δr² + 0.587·Δg² + 0.114·Δb²`; ties → lower index. (The spec says
"linearized"; this plan pins plain sRGB components — it matches the
prototype that generated the site demo, and Task 13 updates the spec
wording.)

**Floyd–Steinberg.** Serpentine scan. Even rows left→right with weights
right 7/16, down-left 3/16, down 5/16, down-right 1/16; odd rows mirrored.
Error accumulates in a float buffer; clamp to 0…255 before matching.

**Bayer 4×4.** `M = [[0,8,2,10],[12,4,14,6],[3,11,1,9],[15,7,13,5]]`;
adjusted channel = `c + (M[y%4][x%4]/16 − 0.5) × 64`, clamped, then nearest.

**Slider → Core Image mapping.** brightness `b`, contrast `c`, saturation
`s`, each in −1…+1: `inputBrightness = 0.25·b`, `inputContrast = 1 + 0.5·c`,
`inputSaturation = 1 + s`.

**Default crop (largest centered 8:5)** for source w×h: if `w·5 > h·8` the
crop is `(x: (w − h·8/5)/2, y: 0, width: h·8/5, height: h)` else
`(x: 0, y: (h − w·5/8)/2, width: w, height: w·5/8)` (integer floor, then
center offset floored).

**Explicit crop snapping.** Given `x,y,w,h`: keep `x,y,w`; `h' =
round(w·5/8)`. Error if `w < 8`, `x + w > sourceWidth`, or `y + h' >
sourceHeight`.

public enum CellConstraints {

    public static func enforceHires(_ buf: inout IndexBuffer, palette: C64Palette)

### Task 5: C64Image packing and rendering

**Files:**
- Create: `Sources/C64Kit/C64Image.swift`
- Test: `Tests/C64KitTests/PackingTests.swift`

**Interfaces:**
- Consumes: `IndexBuffer`, `CellConstraints`, `C64Palette`, `BitmapMode`.
- Produces:

```swift
public struct C64Image: Equatable, Sendable {
    public let mode: BitmapMode
    public let bitmap: [UInt8]        // 8000
    public let screenRAM: [UInt8]     // 1000
    public let colorRAM: [UInt8]?     // 1000, multicolor only, high nibble 0
    public let background: UInt8?     // multicolor only

    /// Pack an already-constraint-satisfying IndexBuffer.
    /// hires: 320×200 input. multicolor: 160×200 + background index.
    public static func pack(hires buf: IndexBuffer) -> C64Image
    public static func pack(multicolor buf: IndexBuffer, background: UInt8) -> C64Image

    /// Decode packed bytes to native-resolution pixels
    /// (320×200 hires, 160×200 multicolor).
    public func render(palette: C64Palette) -> RGBBuffer
}
```

Packing rules (deterministic): **hires** — per cell, foreground = more
frequent index (tie → lower), background = the other; bit 1 = foreground.
Screen byte = `fg << 4 | bg`. Single-color cell: all bits 0, screen byte =
`c << 4 | c`. **Multicolor** — per cell, the up-to-3 non-background indices
sorted by descending count (tie → lower index) map in order to `%01`
(screen upper nibble), `%10` (screen lower nibble), `%11` (color RAM low
nibble); unused slots are 0. Background pixels are `%00`.

- [ ] **Step 1: Write the failing tests** —
  (a) sizes: bitmap 8000 / screen 1000 / colorRAM 1000 or nil / background
  set only for multicolor;
  (b) hand-computed hires cell: 320×200 buffer, all index 6, except cell
  (row 0, col 0) whose left 4 columns are index 1 → cell 0 bitmap bytes
  (offsets 0…7) all `0xF0`, screen[0] == `0x16`; a uniform cell (row 0,
  col 1) → bitmap offsets 8…15 all `0x00`, screen[1] == `0x66`;
  (c) hand-computed multicolor cell: 160×200 all background 0 except cell
  (0,0) columns = [0, 2, 5, 7] on every row → bitmap bytes 0…7 all
  `0b00011011` (0x1B), screenRAM[0] == `0x25`, colorRAM[0] == `0x07`;
  (d) round-trip: for both modes, take the constraint-enforced
  pseudo-random buffer from Task 4's seeded generator, pack, `render`, then
  re-derive each pixel's index by exact RGB equality against the palette —
  must equal the input buffer exactly;
  (e) bitmap addressing: a single index-7 pixel at (x: 12, y: 10) on an
  all-index-0 hires image pins offset `cellRow(1)*320 + cellCol(1)*8 +
  rowInCell(2)` = 330 and bit position 3 (x%8 == 4). NOTE (corrected
  2026-08-08 during implementation): under the normative rule fg = more
  frequent, index 0 wins that cell 63:1, so the cell packs as seven `0xFF`
  bytes with `0xF7` at offset 330 (bit 3 cleared), screen byte `0x07` —
  NOT the originally predicted single `0b00001000` byte, which contradicted
  the rule. All bytes outside the cell are 0x00; assert that too.
- [ ] **Step 2: Run to verify failure** — `swift test --filter PackingTests`
- [ ] **Step 3: Implement** per the pinned layout formulas.
- [ ] **Step 4: Run to verify pass** — `swift test --filter PackingTests`

Pinned program layout (the test's source of truth):

- File = 2-byte load address `0x01 0x08` + program image assembled at $0801.
- BASIC stub at $0801, exactly 13 bytes:
  `0B 08 0A 00 9E 32 30 36 31 00 00 00` is 12 — the implementer derives the
  correct stub for `10 SYS 2061` (link pointer $080B, line 10, token $9E,
  ASCII "2061", line terminator 00, program terminator 00 00) and pins the
  resulting byte string in the test with a comment showing the derivation.
  ML entry is $080D = 2061.
- ML routine (hand-assembled, with the assembly source as a comment block
  in `C64PrgWriter.swift`): `sei`; set `$D011 = $3B` (bitmap mode on);
  `$D016 = $D8` for multicolor / `$C8` for hires; `$D018 = $18` (screen at
  $0400, bitmap at $2000); `$DD00` untouched (bank 0 is the power-on
  default); copy embedded bitmap (8000 B) → $2000, screen (1000 B) → $0400;
  multicolor only: copy color (1000 B) → $D800 and set `$D021` and `$D020`
  to the background index; hires: set `$D020 = 0`; then `jmp *`. Copy loops
  are straightforward indexed loops; data is embedded immediately after the
  routine and addressed absolutely (the writer computes the addresses when
  it lays out the file).
- Size sanity: multicolor ≈ 2 + stub + routine + 8000 + 1000 + 1000 + 1;
  everything loads below $4000? No — $0801 + ~10K reaches ~$2F00, fine
  (BASIC RAM tops at $9FFF). The copy to $2000 overlaps the load region, so
  the writer must place the embedded bitmap data ABOVE $2000 + 8000 = $3F40
  … simplest correct layout instead: put the routine + data so that no copy
  target overlaps the loaded file: load file spans $0801…~$2F55, and $2000
  falls inside it. **Pinned solution:** copy the bitmap BACKWARDS from the
  end (descending copy) — or, simpler and still pinned: relocate all data
  to targets in this order: color→$D800, screen→$0400, THEN bitmap→$2000
  with a descending copy (from the last byte down), which is safe because
  the source block (which starts above $2000 in the loaded image whenever
  the file layout puts 2000-byte routine+screen+color first) ends above the
  target block's end. The implementer must add a test asserting
  no-overlap-corruption: build the PRG, simulate the copies in Swift
  (array ops emulating the routine's exact loop direction over a 64 KB
  byte array), and compare the resulting $2000…$3F3F / $0400…$07E7 /
  $D800…$DBE7 regions against the C64Image fields byte-for-byte.
- `image64 convert in.png -o out.koa --prg out.prg` writes both; `--prg`
  with no `-o` is allowed (PRG only).

- [ ] **Step 1: Write the failing tests** —
  (a) PRG starts `0x01 0x08`; (b) the BASIC-stub bytes equal the pinned
  string; (c) the simulated-execution test above reproduces all three data
  regions exactly for a multicolor image and both regions for hires;
  (d) multicolor routine bytes contain `$D8`-into-`$D016` and hires `$C8`
  (locate via the store-instruction byte pattern pinned in the test);
  (e) CLI: `--prg` writes a file whose first two bytes are `0x01 0x08`,
  and `--json` `outputs` lists it.
- [ ] **Step 2: Run to verify failure** — `swift test --filter PrgWriterTests`
- [ ] **Step 3: Implement** `C64PrgWriter`, the CLI flag, `ViceLauncher`,

### Task 20: Release automation — GitHub Actions builds .app and attaches to Release on tag push

Added 2026-08-09 (maintainer request): give non-developer users a way to
run image64 without cloning the source tree, via a GitHub Release with a
zipped `.app` attached. Unsigned in v1 — the README explains the one-time
right-click-Open Gatekeeper flow. Notarization is a follow-up (needs an
Apple Developer Program membership; out of scope for v1).

**Files:**
- Create: `.github/workflows/release.yml`
- Modify: `README.md` (add a "Download" section right after "Building" —
  4 lines: link to Releases, the first-run right-click note, and the
  same requirement statement as Building).
- Modify: `AGENTS.md` (Commands gains a "Releases" note with the tag-push
  invocation).

**Interfaces:**
- Consumes: `scripts/make-app.sh` (Task 15) — assembles `dist/image64.app`;
  the full `swift test` suite — the workflow runs it before packaging so a
  red tag cannot ship.
- Produces: on `v*` tag push, a public GitHub Release named the tag, with
  one asset `image64-<version>.app.zip`.

**Workflow shape** (`.github/workflows/release.yml`):

```yaml
name: Release
on:
  push:
    tags: ['v*']
  workflow_dispatch: {}
jobs:
  build:
    runs-on: macos-14
    permissions:
      contents: write   # gh release create needs this
    steps:
      - uses: actions/checkout@v4
      - name: Test
        run: swift test
      - name: Build .app bundle
        run: scripts/make-app.sh
      - name: Zip .app (ditto preserves Finder attributes; zip mangles them)
        run: |
          version="${GITHUB_REF_NAME}"
          ditto -c -k --sequesterRsrc --keepParent \
              dist/image64.app "image64-${version}.app.zip"
      - name: Create Release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          version="${GITHUB_REF_NAME}"
          gh release create "${version}" \
              "image64-${version}.app.zip" \
              --title "image64 ${version}" \
              --generate-notes
```

Two pins worth calling out for the implementer:
- `macos-14` — matches the project's minimum deployment target so a build
  that shipped in the .app can actually launch on the users' 14+ machines.
  Running the packaging on a newer runner would silently emit a binary
  whose weak-linked symbols the tool's actual audience does not have.
- `ditto -c -k --sequesterRsrc --keepParent` — `zip` on macOS drops
  extended attributes and resource forks that Finder relies on to
  recognise a `.app` bundle. `ditto` is the correct archive tool on
  macOS; the flags produce a normal `.zip` with the bundle attributes
  intact, so a user double-click-unzipping still gets a real app.

- [ ] **Step 1:** Write `.github/workflows/release.yml` per the shape
  above. The workflow reads `GITHUB_REF_NAME` for the tag version; no
  further version input is needed.
- [ ] **Step 2:** Add a "Download" section to README.md, immediately after
  "Building", of this shape:

      bundles are attached to each [GitHub
      Release](https://github.com/nschneir/image64/releases). Unzip,
      drag to Applications, and — because the bundle is unsigned in v1
      — right-click the app and choose **Open** the first time to
